# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Pico Park-style 2D co-op puzzle platformer built in Unity, using Netcode for GameObjects (NGO) with a dedicated server hosted on GCP.

- Unity: **6000.5.5f1** (`ProjectSettings/ProjectVersion.txt`) — migrated up from an original 2021.3.45f2 baseline; see the Unity 6 migration note below.
- Netcode: `com.unity.netcode.gameobjects` 2.12.0 + `com.unity.transport` 2.6.0 (`Packages/manifest.json`)
- **Active scene structure** (what `EditorBuildSettings.scenes` actually lists, and what `BuildScript.cs` builds): `Assets/Scenes/Bootstrap.unity` → `Lobby.unity` → `Stages/Stage01_Gatekeeper.unity` → `Stage02_BlockCarry.unity` → `Stage03_KeyRelay.unity` → `Stage04_EscapeCountdown.unity` → `Stage05_TwinGatekeeper.unity` (then back to Lobby, cycling), loaded/unloaded additively at runtime by `GameFlowManager` — see "Multi-scene game flow" under Architecture. The Player prefab (`Assets/Prefabs/Player.prefab`) is shared across all of them.
- `Assets/scense/main.unity` (folder name is a typo for "Scenes") was an **earlier single-scene prototype**, no longer in `EditorBuildSettings.scenes` / not built by `BuildScript.cs` — the `.unity` scene file itself has since been deleted (it was never referenced by anything at runtime or by `BuildScript.cs`). **`Assets/Editor/NetworkSetupMenu.cs`, the tooling that built it, was not deleted along with it** — it still owns some assets the live scenes depend on (the Player prefab, `UITheme.cs`, procedural sprites) and remains load-bearing; see "Editor automation" for which parts of that menu are still load-bearing vs. superseded.

## Commands

There is no CLI build/test/lint pipeline in the traditional sense — it's a Unity project — but scene assembly, builds, and compile verification are all scripted rather than manual, via the `Assets/Editor/*.cs` files below. There is no automated test suite.

- **Headless compile check** (run after any script/package/ProjectSettings change, before assuming it works): with the Editor fully closed (a second instance on the same project fails fast on the project lock),
  ```
  "C:\Program Files\Unity\Hub\Editor\6000.5.5f1\Editor\Unity.exe" -batchmode -nographics -quit -projectPath "C:\Users\twinw\Desktop\filerpark" -logFile "<path>.log"
  ```
  The launching process can return **before** Unity actually finishes (package resolution/compilation continues in a detached process) — poll `tasklist` for `Unity.exe` until it's actually gone, then check the log with `grep "error CS"` and confirm `Library/ScriptAssemblies/Assembly-CSharp.dll` exists/was rewritten. A `bee_backend.exe` build-daemon process can outlive Unity itself and hold file locks; `taskkill /F /IM bee_backend.exe` if a cleanup step gets "Device or resource busy".
- **Scene assembly (current)**: `Tools/Coop Setup/Multiplayer Flow/Run All (1-4)` (the label is stale — it now runs 8 steps: Bootstrap, Lobby, Stage01-05, then Build Settings; `Assets/Editor/GameFlowSceneSetup.cs`) rebuilds every scene from scratch and re-registers them in `EditorBuildSettings.scenes` — headless via `-executeMethod GameFlowSceneSetup.RunAll`. **This is destructive-by-overwrite**: each step calls `EditorSceneManager.NewScene(EmptyScene, Single)`, so re-running it discards any manual Inspector tweaks made directly in those scene files since the last run — treat the scenes as generated output, hand-edit only for throwaway testing. Individual `CreateStageNNScene()` methods can also be run alone if only one stage changed.
- **Scene assembly (legacy)**: `Tools/Coop Setup/1-8` (`Assets/Editor/NetworkSetupMenu.cs`) originally targeted `Assets/scense/main.unity` (deleted — see above), and running the full 1-8 sequence today would recreate that scene file from scratch rather than editing anything live. Most of it is superseded, but **step 2 ("Create Player Prefab") is still load-bearing** — it's the only place `Assets/Prefabs/Player.prefab` gets (re)generated, and `Bootstrap.unity` loads that same prefab by path. Re-run it (not `GameFlowSceneSetup`) after changing player art/components.
- **Headless builds**: `Tools/Coop Setup/Build/Dedicated Server (Linux)` / `Dedicated Server (Windows, local testing)` / `Build/Windows Client` (`Assets/Editor/BuildScript.cs`, headless via `-executeMethod BuildScript.<MethodName>`) build from whatever `EditorBuildSettings.scenes` currently lists — no scene list to keep in sync manually. Server builds set `subtarget = Server`, which auto-defines `UNITY_SERVER` (branches `NetworkBootstrapper`). The Windows server build exists purely for local dev-loop testing without needing WSL or a GCP deploy for every iteration — the actual deploy target is still the Linux build. **Both server build methods restore `EditorUserBuildSettings.standaloneBuildSubtarget` to `Player` in a `finally` block after building (success or failure)** — leaving it on `Server` silently makes every subsequent Editor Play Mode session compile with `UNITY_SERVER` defined and behave like a headless server (no local player spawns, nothing visibly wrong except everything just... doesn't happen) until someone notices. Hit this firsthand; don't remove the restore.
- **Headless runtime smoke test**: `Tools/Coop Setup/Debug: Headless Host Smoke Test` (`Assets/Editor/HeadlessSmokeTest.cs`, headless via `-executeMethod HeadlessSmokeTest.Run`, **no** `-quit` flag — the script exits the process itself) opens Bootstrap, actually enters Play Mode, calls `StartHost()`, and observes for ~10s before exiting — catches null-ref/exception-class runtime bugs a compile check can't (e.g. a component touching `NetworkManager.SceneManager` before the network has actually started). Does **not** replace real bot-simulation testing (see below) — it's a much cheaper first check for "does anything throw on startup," run it before a full bot pass. Because Edit→Play triggers a domain reload that wipes ordinary event subscriptions, its `Run()`/reattach logic uses `SessionState` (survives domain reload) instead of just subscribing once — a plain `EditorApplication.update +=` in `Run()` silently never fires again after entering Play Mode and hangs forever with no timeout, which is exactly what happened building this tool the first time.
- **Manual equivalent**: Unity Editor → `File > Build Settings` → platform `Dedicated Server`/`Windows, Mac, Linux`, Target OS `Linux` for the server. The Windows client build doubles as the bot-simulation executable (see below).

## Editor automation

All scene/prefab assembly is done via scripted `[MenuItem]` methods under `Tools/Coop Setup`, not by hand-placing GameObjects in the Inspector — hand-editing `.unity`/`.prefab` YAML directly is riskier than it looks (a single missing trailing space once silently broke `TagManager.asset`'s parser), and because these are static C# methods they're also invokable headlessly via `-executeMethod`, so assembly doesn't require a human driving the Editor GUI. This split across two files, which future changes should keep straight:

- **`Assets/Editor/GameFlowSceneSetup.cs`** (`Tools/Coop Setup/Multiplayer Flow/*`) — builds the *current* `Bootstrap`/`Lobby`/`Stage01_Gatekeeper` scenes and owns `EditorBuildSettings.scenes`. Its Connect/Lobby/Stage UI now applies `UITheme.cs` fully (rounded sprites, real fonts, per-player color-coded scoreboard) via internal helper methods it calls on `NetworkSetupMenu` — see "UI Style Guide implementation" below.
- **`Assets/Editor/NetworkSetupMenu.cs`** (`Tools/Coop Setup/1-8`) — the legacy single-scene prototype (targets `Assets/scense/main.unity`, no longer built). Still the sole owner of `Assets/Prefabs/Player.prefab` generation (step 2) and of the procedural-sprite/UI helper methods (`GetOrCreateRoundedRectSprite`, `GetOrCreatePlayerCharacterSprite`, `CreateOrGetLabel`, `EnsureFolder`, etc. — all `internal static` specifically so `GameFlowSceneSetup.cs` can call them too, instead of duplicating them) that apply the full UI Style Guide. Reused by its own Connect UI and the `WorldMapUI`/`StageIntroUI` stage-select prototype (see "Stage system" below).
- **`Assets/Editor/BuildScript.cs`** (`Tools/Coop Setup/Build/*`) — headless server/client builds, scenes sourced from `EditorBuildSettings.scenes` (see Commands).
- NGO 2.x's `NetworkManager` inspector no longer shows the old Start Host/Server/Client buttons in Play Mode (present in 1.x); `Tools/Coop Setup/Debug: Start Host` (Play-mode-only, gated by a validate function) replaces it by calling `NetworkManager.Singleton.StartHost()` directly.
- **Every scene-creation method in `GameFlowSceneSetup.cs` must reopen-and-resave the scene immediately after its first save** (`ReopenAndResaveToFixNetworkObjectHashes`) if it places any `NetworkObject`. `NetworkObject.GlobalObjectIdHash` is computed by `OnValidate()`, which hasn't run yet by the time a script does `AddComponent<NetworkObject>()` and immediately `EditorSceneManager.SaveScene()` in the same pass — every scene-placed `NetworkObject` gets saved with hash `0`. That's invisible until the scene is actually loaded with 2+ such objects present (true for every stage: button+door+goal, etc.), at which point NGO throws `"X tried to registered with ScenePlacedObjects which already contains the same GlobalObjectIdHash value 0 for Y"`. Caught only by an actual runtime Play session (a headless compile check can't see it) — see `HeadlessSmokeTest.cs` above, which is what surfaced this.

### UI Style Guide implementation

The tokens in "UI Style Guide" (below) aren't just documentation — they're wired into the actual scene:

- **`Assets/Scripts/UI/UITheme.cs`** — the single source of truth for the style guide's colors/font paths as C# constants (`ColorPrimary`, `ColorFg`, `FontHeadingPath`, etc.). Both `NetworkSetupMenu.cs` and any gameplay script (e.g. `CreateCoopTest`'s button/goal-zone colors) reference these instead of hardcoding hex values.
- **`Assets/Fonts/`** — the actual `Dosis-ExtraBold.ttf` (instanced from Google's variable-font source at `wght=800` via `fontTools.varLib.instancer`, since Dosis only ships as a variable font upstream) and `MPLUS1p-Bold.ttf`/`MPLUS1p-Medium.ttf`, pulled directly from `google/fonts` on GitHub, with their `OFL.txt` licenses alongside. Dosis has **no Hangul glyphs** — it's used only for the Latin title/logo (`TitleLabel`, "FILER PARK"); any Korean-facing label (the connect button, future dialogs) must use M PLUS 1p instead, which covers Hangul.
- **`NetworkSetupMenu.GetOrCreatePlayerCharacterSprite()`** — procedurally draws the player sprite (a filled circle in white, an outline ring in `UITheme.ColorFg`, two simple round eyes with a highlight dot) instead of using a flat placeholder square. White fill is deliberate: `PlayerColorNGO` tints the whole sprite by multiplying `SpriteRenderer.color`, and white pixels are the only ones that take on the per-player color cleanly — the dark outline/eyes stay legible under any tint because multiplying by near-black stays near-black.
- **`NetworkSetupMenu.GetOrCreateRoundedRectSprite()`** — bakes a 9-sliceable rounded-rect PNG (rounded-box SDF, correct `spriteBorder` for the corner radius) for button backgrounds, used instead of Unity's built-in `UI/Skin/UISprite.psd` so the corner radius/border thickness/border color actually match the style guide rather than Unity's default skin. Takes an optional `radius`/`borderThickness` so callers can bake distinct variants at the same call site pattern (e.g. `UI_ButtonPrimary.png` at the default 28/10 vs. the bigger `UI_CardPanel.png` panel at 40/6).
- **World-space (non-UI) rounded sprites need `SpriteRenderer.drawMode = SpriteDrawMode.Sliced` + `.size`, not `transform.localScale`** — scaling a rounded sprite via `localScale` stretches the corners along with the rest of it, defeating the rounding. `GameFlowSceneSetup.ApplySlicedSprite()` is the helper; `Stage01_Gatekeeper`'s button/door/goal-zone all use it. Colliders on those objects are sized directly in world units to match (`BoxCollider2D.size`), since `localScale` is left at 1.
- **Tintable vs. fixed-color rounded sprites**: `CoopDoorNGO` recolors its `SpriteRenderer.color` at runtime (multiply tint, open/closed state) — if it used the green/white `UI_ButtonPrimary.png` badge sprite, the fill and border would tint to two different, wrong-looking colors. Runtime-tinted world objects need a **flat white-on-white** rounded sprite instead (`UI_RoundedWhite.png`, `fillColor == borderColor == Color.white`) so a multiply tint stays a single clean color. Statically-colored objects (the button, never recolored after scene build) can use the two-tone badge sprite directly.
- **`StageClearUI.cs`** uses legacy `UnityEngine.UI.Text`, not TMP — it originally used `TMP_Text`, which renders blank text in this project (TMP Essentials was never imported, same reason the rest of the UI avoids TMP).

## Unity 6 migration notes

The project was originally scaffolded against Unity 2021.3.45f2 and later moved to 6000.5.5f1; a few things fell out along the way that are worth knowing if `manifest.json` or scripts changed since then start throwing errors again:

- `com.unity.modules.vr` (and the rest of the boilerplate `com.unity.modules.*` block copied from the original Alteruna-derived `manifest.json`) is gone from the Unity 6 package registry — package resolution fails outright if it's present. None of those built-in modules need to be listed explicitly; Unity resolves what it actually needs.
- `com.unity.2d.animation`, `com.unity.2d.spriteshape`, and `com.unity.2d.psdimporter` don't compile on Unity 6000.5's API (`Object.GetInstanceID()`/`TreeView` obsoletions turned into hard errors) and aren't used by this project — removed rather than fixed.
- `Rigidbody2D.velocity` is obsolete in Unity 6; use `linearVelocity` (see `PlayerMovementNGO.cs`).
- `TagManager.asset`'s layer list is YAML `- ` (dash-space) per empty entry; a bare `-` with no trailing space fails to parse and Unity silently falls back to default tags/layers instead of erroring loudly — caught only by actually opening the project, not by eyeballing the diff.

## Architecture

**Server-authoritative throughout.** The server (or host) owns physics and game-state decisions; clients send input and render whatever the server decides. This is deliberate — Pico Park-style stacking/pushing between players only works reliably if one place resolves the physics.

### Multi-scene game flow (Bootstrap / Lobby / Stage)

The live flow is `Bootstrap.unity` (always loaded) → additively loads `Lobby.unity` → additively loads a stage scene (e.g. `Stages/Stage01_Gatekeeper.unity`) → back to `Lobby.unity`, repeat. All orchestration lives in one place so individual scenes/scripts can stay portable and ignorant of each other:

- **`Assets/Scripts/Network/GameFlowManager.cs`** — a `NetworkBehaviour` placed directly in the Bootstrap scene (not on the `NetworkManager` GameObject — scene-placed `NetworkObject`s auto-spawn when the server starts, the same trick `CoopButtonNGO` etc. rely on; `NetworkManager`'s own GameObject is never spawned, so it *can't* host `NetworkVariable`s/RPCs itself). Owns a `GamePhase` (`Lobby`/`InStage`/`Results`) `NetworkVariable`, `currentStageIndex`, a `lobbyCountdownRemaining` timer, and a server-only `Dictionary<ulong,int> scores`. `stageSceneNames` is the **single list to edit** to add/reorder stages. Bootstrap's own scene is never unloaded and stays the active scene throughout (so spawned objects like players stay parented to it even while Lobby/Stage get additively unloaded).
- **Scene transitions are sequenced, not fired back-to-back**: calling `NetworkManager.SceneManager.UnloadScene()` and `LoadScene()` in the same frame makes NGO silently drop the second call (no exception — it just looks like the transition hung, only visible by inspecting the ignored `SceneEventProgressStatus` return value). `BeginUnloadScene()`/`BeginLoadScene()` + a `pendingLoadSceneName` field queue the load until `OnUnloadEventCompleted` fires for the unload. Verified end-to-end against the real GCP dedicated server with 5 concurrent bot clients cycling Lobby → Stage01 → Results → Lobby repeatedly.
- **Portability principle**: a stage scene's `StageManagerNGO` only knows its own `GoalZoneNGO` and calls `GameFlowManager.Instance.NotifyStageCleared()` on clear — it has no idea what stage comes next, what the score is, or how to get back to the lobby. Adding a stage is: one new scene file + one line in `stageSceneNames` + one line in Build Settings (`Tools/Coop Setup/Multiplayer Flow/4`); nothing else needs touching. See `Assets/Editor/GameFlowSceneSetup.cs`'s header comment for the exact steps.
- **Player repositioning**: `PlayerSetupNGO.MoveToSpawnPoint()` (public) finds `SpawnPoint`-tagged objects in whatever scene is *currently loaded* and places the player there — it has no notion of which scene that is. `GameFlowManager` calls it for every connected client from `NetworkManager.SceneManager.OnLoadEventCompleted` (not right after calling `LoadScene` — the load isn't done yet at that point) and again from `OnClientConnectedCallback` for players joining mid-lobby.
- **Scoreboard propagation**: `GameFlowManager` pushes score updates via a `ClientRpc` into `ScoreboardUI.UpdateScoreboard()`, a **static** method backed by a static `Dictionary` — necessary because the RPC can fire while the Lobby scene (and its `ScoreboardUI` instance) isn't currently loaded; the static cache holds the latest values until a `ScoreboardUI` instance in a freshly-loaded Lobby scene starts reading it in `Update()`. `LobbyUI` similarly just polls `GameFlowManager.Instance`'s `NetworkVariable`s in `Update()` — neither UI script touches game logic.
- **`Assets/Scripts/Network/NetworkBootstrapper.cs`** — entry point attached to the `NetworkManager` GameObject in the Bootstrap scene. Branches on the `UNITY_SERVER` compile flag: a Dedicated Server build calls `NetworkManager.Singleton.StartServer()` in `Start()` automatically; a regular client build waits and calls `StartClient()` from `ConnectToServer()`, wired to a UI button's `OnClick`. `startMenuUI` (assigned in the Inspector) is hidden once the client connects.

### Player & co-op mechanics (shared across all scenes)

- **`Assets/Scripts/Player/PlayerMovementNGO.cs`** — movement/jump. The owning client writes raw horizontal input into a `NetworkVariable<float>` (`WritePermission.Owner`); only the server reads it in `FixedUpdate()` and applies it to `Rigidbody2D.velocity`. Jump is a `ServerRpc` the server validates against a ground-check `OverlapCircle` before applying. On `OnNetworkSpawn()`, the Rigidbody2D is set `Kinematic` on every non-server instance so local physics never fights the server's authoritative position — `NetworkTransform` is the only thing that should move a non-server instance. Ground detection expects a child `groundCheck` Transform and objects on the `Ground` layer.
- **`Assets/Scripts/Coop/CoopButtonNGO.cs`** / **`CoopDoorNGO.cs`** — a button counts overlapping `Player`-tagged colliders server-side only (`if (!IsServer) return;` guards both trigger callbacks) and fires `OnButtonPress`/`OnButtonRelease` `UnityEvent`s, wired in the Inspector to a door's `AddPress()`/`RemovePress()`. The door tracks `requiredButtons` vs. currently-pressed count and writes the result into a `NetworkVariable<bool> isOpen` (`WritePermission.Server`), whose `OnValueChanged` callback drives the open/closed visuals identically on every client, including late joiners.
- **`Assets/Scripts/Coop/GoalZoneNGO.cs`** — the "everyone reach here at once" condition: tracks currently-overlapping `Player`-tagged colliders in a `HashSet`, and once the count matches `ConnectedClientsIds.Count` (server-side), flips a `NetworkVariable<bool> stageCleared`. `StageManagerNGO` subscribes to that value-changed event and forwards it to `GameFlowManager.NotifyStageCleared()` — it's the only bridge between "stage-local gameplay" and "global flow state."
- All of the above require a `NetworkObject` component on their GameObject to function — without one, `IsServer`/`NetworkVariable`s won't resolve correctly.

### Bot simulation (solo-dev multiplayer testing)

Because co-op mechanics can't be validated solo without a second real player, `-bot` client processes stand in for human partners:

- **`Assets/Scripts/Network/BotProcess.cs`** — static class that parses `Environment.GetCommandLineArgs()` once at startup (`RuntimeInitializeOnLoadMethod`). Sets `BotProcess.IsBot` from the `-bot` flag, and optional `-serverip <addr>` / `-serverport <port>` overrides.
- **`Assets/Scripts/Network/NetworkBootstrapper.cs`** — in the non-`UNITY_SERVER` branch, if `BotProcess.IsBot` is true it overrides the `UnityTransport` connection address (defaults to `127.0.0.1` so bots connect to a local Editor Play-mode host) and immediately calls `ConnectToServer()` instead of waiting for a UI click.
- **`Assets/Scripts/Player/BotController.cs`** — a `NetworkBehaviour` on the Player prefab. In `OnNetworkSpawn()`, disables itself unless `IsOwner && BotProcess.IsBot`. When active, generates `HorizontalInput`/`JumpRequested` every frame instead of reading the keyboard. Default mode is **`StageAuto`**, which detects the loaded stage by probing for its gimmick component (`Object.FindAnyObjectByType<T>()`, cached and rescanned every 0.5s / on scene change rather than every frame) and then executes that stage's **actual co-op solution**, not a generic approximation:
  - *S1 Gatekeeper* (`CoopDoorNGO`+`GoalZoneNGO`): rank-0 stands on the button to hold the door open; everyone else passes through it.
  - *S2 Block Carry* (`PushableBlockNGO`): all bots push the block to its target, then cross the resulting bridge to the goal. (All-push, not a designated subset — one mistimed pusher would otherwise stall the required-count gate forever.)
  - *S3 Key Relay* (`CarryableKeyNGO`): rank-0 fetches the key and holds the door open until every other bot is across, then crosses last (solo = trivially balanced). The others cross the seesaw **one at a time via an emergent balance rule** — only step onto the near half when it isn't heavier than the far half — which keeps `|left−right| ≤ 1` so the seesaw stays level (< `tiltThreshold`).
  - *S4 Escape Countdown* (`RisingHazardNGO`): run right toward the goal, **stop once safely inside it** (crucial — bots used to march straight through and off the far cliff into a soft-lock), pacing to the slowest teammate so everyone converges into the goal together.
  - Role ranking (where used) is derived independently by every client from `OwnerClientId` ordering — no server-broadcast role assignment / `NetworkVariable` plumbing, since all clients see the same connected-clients set deterministically. This is the simpler alternative to the director `Docs/Stages/bot-coordination.md` originally proposed.
  - **Jumping**: `StageAuto` does **not** random-jump (no stage needs a jump, and random jumps knocked bots off the block-bridge/seesaw into pits). Instead it uses a purposeful *unstick* jump that fires only when a bot is trying to move but isn't making progress (a small ledge), and only in contexts where that can happen (seesaw crossing) — off during pushing so pushers don't jump off the block. `Patrol`/`FollowNearest` remain as manual test modes and keep the old random jump.
  - **Human-like variance (cosmetic only)**: each bot rolls three fixed personality traits once at `OnNetworkSpawn()` — `reflexSpeedScale` (0.85–1.0, a per-bot top-speed multiplier so bots don't all move at identical pixel-perfect velocity), `arrivalTolerance` (0.15–0.25, replaces `MoveToward`'s old hardcoded 0.2f dead-zone so bots don't all stop at the exact same distance from a target), and `reactionDelay` (0.05–0.35s, a hesitation applied at explicit "objective just changed" transitions — the block reaching `isInPlace` in Stage 2, the door flipping `isOpen` in Stage 3 — so the whole group doesn't turn in perfect frame-locked unison). Deliberately scoped to **timing/magnitude only, never target coordinates or gating logic** — `reflexSpeedScale` is skipped during `recoverySuppressed` (the block-push formation) so it can't weaken the required-pushers gate, and none of the three touch the unstick-recovery layer. Random per-bot idle jitter/idle-jumping was considered and rejected: the existing code comments on why random jumps were removed (knocks bots off the block bridge/seesaw, jostles the goal zone) apply just as much to a "look alive while waiting" idle animation, so waiting states stay perfectly still.
  - **Same `reactionDelay` trait also gates stage-entry**: `UpdateStageAuto()` tracks `stageEnteredAt`, set the frame `goal` transitions from null (Lobby/scene-transition gap) to non-null (a stage just finished loading) — until `reactionDelay` elapses past that moment, the bot holds still (`HorizontalInput = 0f`) instead of immediately executing its per-stage solution. Without this, bots visibly begin the objectively-optimal path on the exact first frame a stage loads, which is one of the most obvious "this is clearly a script" tells a human observer would notice. Purely a delayed start, not a different decision — Stage 4's hazard has a 3s `startDelay` regardless, so this adds no real time pressure. Verified via `Stage05BotVerify` after adding this (still clears).
  - **Stage 4's `AllowedLead` is now situational, not a bare constant**: `UpdateEscape()` used to cap how far a bot could lead the team's slowest member at a fixed 2.5 units. It's now computed each frame from the hazard's actual distance to that slowest member (`Mathf.Clamp(hazardDistanceToSlowest * HazardProximityToLeadScale, MinAllowedLead, MaxAllowedLead)`) — bots range further ahead while the wall is still distant and tighten up as it closes in on whoever's behind, the way a person keeping an eye on a real threat would, instead of always using the same fixed cushion regardless of context. Bounded to `[1.5, 4]` (straddling the old 2.5 constant) specifically so this can only ever tighten or loosen the existing safety margin within a similar range, never break the stage's core premise that bots are far faster than the 0.3u/s wall — a genuine per-stage strategy upgrade, not cosmetic timing/speed variance like the traits above.
- **`Assets/Scripts/Player/PlayerMovementNGO.cs`** — `Update()` checks for a sibling `BotController`; if present and enabled, it feeds `horizontalInput`/jump from the bot instead of `Input`. Everything downstream (the `NetworkVariable`, the `ServerRpc`) is identical to the human path, so bots exercise real network code, not a mock.

**Workflow**: build a regular client once (`Tools/Coop Setup/Build/Windows Client` or `File > Build Settings` → `Windows, Mac, Linux`) → `Tools/Coop Setup/Bot Simulation/Set Bot Client Build Path...` to point at the `.exe` → open `Bootstrap.unity`, enter Play mode, and `Tools/Coop Setup/Debug: Start Host` → `Tools/Coop Setup/Bot Simulation/Launch 1/2/3 Bot Client(s)` to spawn headless partners that auto-connect over `127.0.0.1:7777`. `Stop All Bot Clients` kills processes by matching the exe's filename (note: this also kills any other running copy of that same build). Bots only need the code path above; they don't require the GCP server and aren't wired into it.

**Gotcha — `ClientBuild/filerpark.exe` goes stale after any scene regeneration**: bot clients connect against whatever scenes/prefabs are baked into that one compiled build, while a headless host (Editor Play mode / `Tools/Coop Setup/Debug: Start Host`) always runs the *current* project state. If the scenes were regenerated since the client was last built (e.g. `GameFlowSceneSetup.RunAll()` after adding a stage — see Stage 5's addition, which did exactly this), the connecting bot silently fails: NGO throws `NullReferenceException` inside `NetworkObject.Deserialize`/`SceneEventData.SynchronizeSceneNetworkObjects` on the **client's** `Player.log` (`%USERPROFILE%\AppData\LocalLow\<companyName>\<productName>\Player.log`, from `ProjectSettings.asset`) while the host-side log just shows the client's connected-count never advancing past the host itself — reads exactly like a gameplay/network regression (a stuck required-pushers gate, a stage that "never loads") until you check client vs. build mtimes. Symptom found and root-caused this way: Stage 2 (`PushableBlockNGO`) appeared to hard-regress after the Stage 5 commit — `overlap=0` forever even with bots running — but the block code hadn't changed; the client build just predated that commit's full scene regen. Rebuilding `Tools/Coop Setup/Build/Windows Client` and re-running fixed it immediately. **Rebuild the client after every `RunAll`/per-stage scene regeneration, not just after script changes**, before trusting any bot-verify tool's failure as a real regression.

### Stages 2-4 (Block Carry / Key Relay / Escape Countdown)

All 4 missions from `Docs/Stages/*.md` are now implemented and wired into `GameFlowManager.stageSceneNames` (`Stage01_Gatekeeper` → `Stage02_BlockCarry` → `Stage03_KeyRelay` → `Stage04_EscapeCountdown`, cycling back to 1), each built by its own `GameFlowSceneSetup.CreateStageNNScene()` method. Design docs simplified some mechanics specifically to stay bot-testable (see `Docs/Stages/bot-coordination.md` §5's own caveat about precision-timed actions) — most notably Stage 2 bridges a pit with the pushable block instead of requiring a precision-timed stack, since `BotController`'s jump is a random timer that can't reliably land on top of another bot.

- **`Assets/Scripts/Coop/PushableBlockNGO.cs`** (Stage 2) — same overlap-counting pattern as `CoopButtonNGO`, gated by `requiredPushers` (60% of connected players, scaled in `OnNetworkSpawn()`). Moves toward `targetPoint` while enough players overlap its push-trigger; sets `isInPlace` on arrival. The push-trigger must be sized well past the solid collider (`pushStandoffDistance` / the trigger width in `GameFlowSceneSetup`) — too tight and bots physically can't stand close enough to register as "pushing," a real bug hit during 5-bot testing.
- **`Assets/Scripts/Coop/CarryableKeyNGO.cs`** + **`KeyDoorNGO.cs`** (Stage 3) — a shared key tracked by `carrierClientId`; server validates pickup distance via `RequestPickupServerRpc`/`RequestDropServerRpc`. `KeyDoorNGO` opens whenever the key (regardless of carrier) is within `openRange` of the door, using the same tintable-white-sprite + `UITheme.ColorIce` treatment as `CoopDoorNGO`.
- **`Assets/Scripts/Coop/SeesawPlatformNGO.cs`** (Stage 3) — child `SeesawSideZone` triggers (one per side, since a single parent collider can't tell which side a trigger event came from) report overlap counts up to the parent, which tilts (`transform.rotation`) when the left/right difference exceeds `tiltThreshold`.
- **`Assets/Scripts/Coop/RisingHazardNGO.cs`** (Stage 4) — advances on `+X` at `riseSpeed` after `startDelay`; touching it calls `StageManagerNGO.NotifyFailure()`. Implements the design doc's "wall" variant rather than rising lava (see the script's own comment for why: a horizontal wall makes "who's furthest behind" and "who gets caught first" the same thing, matching the stage's "match the slowest teammate" intent without needing separate tiered terrain). Its danger-red color is a deliberate exception to the UI Style Guide's palette — hazard/danger signaling doesn't read through brand green/blue.
- **`Assets/Scripts/Network/StageManagerNGO.cs`** gained an optional `hasFailCondition`/`hazard` pair (off by default) for Stage 4's reset-on-failure path — resets all players to their spawn points and the hazard to its start position, entirely locally (doesn't touch `GameFlowManager`'s score/phase state, since a mid-stage retry isn't a lobby-level event).
- **Fail banner**: until now, catching the hazard only played `SfxId.StageFail` and silently teleported everyone back to spawn — no on-screen explanation for what just happened, unlike the clear banner's "CLEAR!" card. `RisingHazardNGO.PlayFailSfxClientRpc()` (already a `ClientRpc`, since only the server's trigger event knows a failure happened) now also calls `StageClearUI.ShowFailBanner()`, which shows a "다시 도전!" card (red/danger-toned per the style guide's hazard-color exception, `UIPunchIn` pop-in for consistency with every other card) for 1.5s via `WaitForSecondsRealtime` before auto-hiding. `BuildStageUI()` builds this banner for every stage scene (matching the clear banner's already-portable pattern) even though only Stage 4 (`hasFailCondition == true`) ever triggers it.
- **Verified state** (per the implementing commits): Stage 1 clears reliably via repeated 5-bot runs against the real GCP server; Stage 2 works consistently after several real bugs found this way (an un-walkable 0.8-unit step on the block's top surface, a push-trigger too tight to fit 3+ bots, a missing safety-net floor under the pit — a jostled bot fell through to Y≈-294802 in one run before that was added). Stage 3 needed two more fixes before it would even load/clear (`2b96135`): `SeesawSideZone` was a second class living inside `SeesawPlatformNGO.cs`, whose filename/class mismatch raced domain-reload registration during headless scene generation and produced a scene with a "Missing Script" component that corrupted the built Stage03 scene file on the dedicated server; and the key carrier could permanently deadlock a few units from the key's spawn point instead of walking it to the door. All 4 stages now clear reliably in a continuous 5-bot loop (Stage1→2→3→4→Stage1…) against the real GCP server, verified over ~9 minutes of consecutive cycles.
- **Mid-session disconnect (edge case, verified against the real GCP server)**: killing 2 of 5 connected bot clients mid-Stage03 (a hard process kill, not a graceful quit) did not soft-lock the stage or throw any server-side exception — `GoalZoneNGO`'s clear check and `PushableBlockNGO`'s `requiredPushers` scaling both key off the live `ConnectedClientsIds.Count`, and `BotController`'s rank (used for Stage 3's carrier/waiter role split) is recomputed independently by each remaining client every 0.5s, so the group re-converged on a valid role assignment without any disconnect-specific handling code. The stage cleared with the remaining 3, and the game continued cycling Stage4→1→2→3→… normally at the reduced player count with zero errors across several more full loops.
- **Late join mid-session (edge case, verified against the real GCP server)**: connecting 2 new bot clients while the existing group was transitioning out of a just-cleared stage worked with no special-case code needed — the new clients' `PlayerObject`s spawn and `PlayerSetupNGO.OnNetworkSpawn()` positions them at whatever scene's `SpawnPoint`s are currently loaded regardless of `GameFlowManager`'s phase, and once the group synced back in Lobby the connected count read 5 and every subsequent stage cleared normally at full strength.
- **Stage 2 "stall at low bot counts" — root-caused: a stale `ClientBuild/filerpark.exe`, not a gameplay/physics flake.** This was initially observed as an intermittent-looking hang (a full-rotation bot test and an isolated 2-bot Stage 2 test both stalled at `overlap=0 required=N` forever, though occasionally a rerun "just cleared"), which read like a timing-dependent physics flake in `PushableBlockNGO`'s Kinematic-`Rigidbody2D`-push mechanic. It isn't: the connecting bot clients' `Player.log` (`%USERPROFILE%\AppData\LocalLow\<companyName>\<productName>\Player.log`) showed `NullReferenceException` inside `Unity.Netcode.NetworkObject.Deserialize`/`SceneEventData.SynchronizeSceneNetworkObjects` — the bots were never actually joining the network session at all (the host-side connected count never rose above 1), so `overlap` was zero because there was no second player present to overlap anything, not because pushing was unreliable. See the `ClientBuild` staleness gotcha directly above the "Stages 2-4" heading: the build predated the Stage 5 commit's full scene regen, so its baked-in scene/`NetworkObject` layout no longer matched the live host. Rebuilding `Tools/Coop Setup/Build/Windows Client` and rerunning `Stage02BotVerify` cleared normally (host+2 bots all connected, block reached `isInPlace`, stage cleared) — no code change to `PushableBlockNGO.cs`/`BotController.cs` was needed for this specific symptom. (The occasional "just clears on rerun" is consistent with this too — whichever run happened to use a `ClientBuild` that was already up to date, or a stale build combined with a scene that happened to still match closely enough for that particular client, would connect fine.) Worth remembering next time this class of symptom shows up: check the client's own `Player.log` for a network exception, and check `ClientBuild` mtime vs. the last scene regen, **before** suspecting the gameplay code.
- **A second, real bug found via `FullRotationBotVerify` after the staleness issue above was ruled out**: `PlayerMovementNGO.FixedUpdate()`'s fall-recovery safety net (`transform.position.y < FallLimitY` → `PlayerSetupNGO.MoveToSpawnPoint()`) retried every physics tick (50/s) with no cooldown. During the brief scene-transition window where the old scene has unloaded but the next stage hasn't finished loading, there are momentarily zero `SpawnPoint`-tagged objects in any loaded scene anywhere — a player whose gravity carried them below `FallLimitY` in exactly that window got stuck spamming the "no SpawnPoint tag" warning every tick instead of recovering promptly once a stage with spawn points actually loaded. A `FullRotationBotVerify` run that should clear 5 stages in a few minutes instead spent nearly its entire 8-minute budget stuck in Stage 1 with a ~358,000-line log dominated by that one repeated warning. Fixed by rate-limiting the retry to twice a second (`FallRecoveryRetryInterval`, `Assets/Scripts/Player/PlayerMovementNGO.cs`) — recovery is still effectively immediate once spawn points exist, just without the per-tick busy-loop in the gap where they don't. **Measured impact**: a rerun with the fix (fresh `ClientBuild`) reached Stage 3 (`currentStageIndex == 2`) with only ~15,500 log lines total, vs. the previous run's 358,000 lines to barely reach Stage 2 — Stages 1 and 2 now clear in roughly the time they should. **The Stage 3 stall that followed is not a game bug — it's an artifact of `StartHost()`-based local test tooling, root-caused and explained below.**

- **Root cause**: every local bot-verify tool in this file (`HeadlessSmokeTest`, `Stage05BotVerify`, `FullRotationBotVerify`, and the Stage03BotVerify used to diagnose this) calls `NetworkManager.Singleton.StartHost()` to stand up a test server inside the Editor process. `StartHost()` is server **+ client** combined, so it spawns a real `PlayerObject` for itself — with `OwnerClientId 0`, the lowest possible ID. `BotController.GetMyRank()` ranks by ascending `OwnerClientId`, so **the host's own idle player is always rank 0**, and it never runs `BotController` logic at all (`BotProcess.IsBot` is false for a plain `-batchmode` Editor process with no `-bot` flag, so `enabled = BotProcess.IsBot` leaves it permanently disabled). Compare `NetworkBootstrapper.cs`'s `UNITY_SERVER` branch — the actual dedicated server build calls `StartServer()`, **not** `StartHost()`, which spawns no player object for itself at all. The real deployment topology (dedicated server + N real bot/human clients) never has this phantom rank-0 player; only this Editor-hosted local test setup does.
- **Why this breaks Stage 3 specifically but not Stages 1/2/5**: `BotController.UpdateKeyRelay()` hard-codes `if (rank == 0) { UpdateKeyCarrier(...); return; }` — only rank 0 ever fetches the key, opens the door, and lets everyone else across. With the phantom idle host permanently occupying rank 0, nobody ever fetches the key, `KeyDoorNGO.isOpen` never flips true even once (confirmed: zero `[KeyDoor]` log lines across a 744-second stall), and every other bot waits forever at `HorizontalInput = 0f` for a door that can never open — a real, reproducible, 100%-deterministic deadlock, but one this test methodology causes rather than reveals. Stage 1 (`UpdateGatekeeper`) has the identical `rank == 0` structure but happens to "clear" anyway, for an unrelated reason already documented above (its goal zone is deliberately sized to cover the entire spawn+patrol range, so the "all players in the goal simultaneously" condition can trivially become true without anyone actually crossing the door). Stage 2 (`UpdateBlockPush`) has no rank-specific requirement at all — every bot pushes together — so an idle rank-0 host merely reduces the effective pusher count by one, which `requiredPushers` scaling already tolerates.
- **What this means for actual verification confidence**: Stages 1 and 2 clearing in these local tests is real signal (confirmed working, independent of the rank-0 artifact). Stage 5 clearing in `Stage05BotVerify` is also real signal — `UpdateTwinGatekeeper` needs rank 0 *and* rank 1, and that test happened to launch exactly 2 bots against a host, giving the bots ranks 1 and 2 while the host absorbs rank 0 as an unnecessary-but-harmless third door-opener slot that never gets filled (the door only requires the two bots, who land on ranks 1/2 and correctly treat themselves as needing partner coordination). A local reflection-based attempt to also make the `StartHost()` process act as a real bot (forcing `BotProcess.IsBot = true` before spawn) was tried and reverted — it produced an inconclusive result (a *different* stage stalled that run, most plausibly local resource contention after hours of continuous Editor use) rather than a clean confirmation, and added a hacky code path for a marginal payoff.
- **Resolved via the real thing instead**: deployed this session's build (fall-recovery fix + Stage 5 + all other changes) to the actual GCP dedicated server (`filerpark-game-server`, replacing a *currently-running* deployment that was independently found to be exhibiting the exact fall-recovery spam — 2011 of 2615 log lines, with every connected client timing out on scene loads — strong real-world confirmation the bug mattered) and ran 5 real bot clients against it end-to-end. Result: **Stage1→2→3→4→5→Lobby→Stage1→2→3→4 cleared repeatedly across multiple full cycles (8 stage-clears observed, zero exceptions, zero log spam) before the bots were stopped** — Stage 3 in particular cleared twice, with a real bot (not a phantom host) correctly taking rank 0, fetching the key, and opening `KeyDoor1`, exactly as the rank-0 analysis predicted. This is the direct GCP/N-bot verification Stages 1-4 originally received, now extended to cover Stage 5 and this session's fixes. The server was left running afterward (idling with the fixed build deployed, no players connected) rather than reverted.

### Stage 5 (Twin Gatekeeper)

A 5th stage added to grow the content rotation beyond the original 4-mission design doc set, built as a **remix of already-verified components** rather than a new mechanic — deliberately, to add real replay-content without the implementation/verification risk of a brand-new `NetworkBehaviour`:

- `GameFlowSceneSetup.CreateStage05Scene()` reuses `CoopButtonNGO`/`CoopDoorNGO`/`GoalZoneNGO` (Stage 1's exact components, including Stage 1's already-proven "goal zone wide enough to cover the whole spawn+patrol range" layout formula) but places **two** buttons instead of one, both wired to the same door, and leaves `CoopDoorNGO.requiredButtons` at its actual default (`2`) instead of the `1` Stage 1 explicitly lowers it to — a value that existed in the component from the start but no shipped stage had used until now.
- `BotController.UpdateGatekeeper()` branches on `coopDoor.requiredButtons > 1` to route into `UpdateTwinGatekeeper()`: rank 0 and rank 1 each head to a *different* button (`gatekeeperButtons`, a `RefreshStageRefs()`-cached array of every `CoopButtonNGO` in the scene, **sorted by x-position** — `FindObjectsByType`'s own array order is an implementation detail that isn't guaranteed to match across clients, but every client loads the identical scene file, so sorting by x-position is what actually guarantees every client's rank→button assignment agrees), everyone else waits then crosses once the door opens. Same "some hold, the rest pass through" shape as Stage 1, just requiring two different people to coordinate simultaneously instead of one.
  - **Distance-based assignment, not a blind rank→button map**: `rank == 0`/`rank == 1` still decide *who* holds a button, but *which* button each of them takes is decided by actual proximity, not fixed index order — a real player standing right next to button 1 wouldn't walk past it to go hold button 0 just because they connected first. Both candidates' positions are compared against both buttons, and the two swap their default (`rank == index`) assignment only if **both** independently agree the cross-assignment is closer by a full `TwinGatekeeperSwapMargin` (1 unit). This margin exists because the comparison uses `PlayerSetupNGO.ActivePlayers` positions, which for a remote bot are `NetworkTransform`-interpolated and can read slightly differently between clients — a partial/disagreeing swap would leave one button unclaimed. Requiring a full-unit margin on a mutual (not one-sided) condition means any disagreement between clients only suppresses the swap, never causes it, so the worst case degrades to the original always-correct rank-order assignment rather than a stall. `FindPlayerByRank()` (next to `GetMyRank()`) is the reverse lookup this needed.
- Wired into `GameFlowManager.stageSceneNames`, `ConfigureBuildSettingsScenes()`, `GameFlowSceneSetup.RunAll()`, and `NetworkSetupMenu.CreateStageCatalog()` (`Assets/StageData/Stage05_TwinGatekeeper.asset`, `StageTheme.SimultaneousSwitches` — same theme as Stage 1, since it genuinely is the same theme at higher coordination difficulty) — see "Two sources of truth" below for why both the `stageSceneNames` array and the catalog needed the entry.
- **`Assets/Editor/Stage05BotVerify.cs`** (`Tools/Coop Setup/Debug: Stage05 Bot Verify`, headless via `-executeMethod Stage05BotVerify.Run`) — a `HeadlessSmokeTest`-style tool built specifically to verify this stage actually clears, not just that it loads without throwing (the smoke test's own 10s host-only observation can't reach a stage-clear at all). It opens Bootstrap, **overrides the in-memory `GameFlowManager.stageSceneNames` to `{ "Stage05_TwinGatekeeper" }`** right after `OpenScene` (before entering Play mode — Unity carries edited scene-object state through the Play button's domain reload, so this needs no on-disk edit to `Bootstrap.unity` and nothing to revert afterward), then starts a host, launches 2 real built bot clients (`ClientBuild/filerpark.exe -bot`), and watches for `GameFlowManager.phase` to reach `Results` (i.e. `NotifyStageCleared()` actually fired). **Run and passed**: 2 bots correctly split onto the two separate buttons and cleared the stage. This is real functional verification (both buttons held simultaneously, door opened, goal reached), but it's still short of the 4-6 bot / multi-cycle GCP real-server testing Stages 1-4 received (see `Docs/Stages/README.md`'s Stage 5 row) — treat Stage 5 as functionally verified, not yet stress-tested at the same level as the original four.
- **`Assets/Editor/FullRotationBotVerify.cs`** (`Tools/Coop Setup/Debug: Full Rotation Bot Verify (1-5)`) — same `HeadlessSmokeTest`/`Stage05BotVerify` pattern, but deliberately does **not** override `stageSceneNames`: it launches 4 real bot clients against the actual full 5-stage rotation and watches for `currentStageIndex == 4` (Stage 5) to reach `Results`, i.e. proof Stage 5 clears reachable via natural sequential progression through Stages 1-4, not just in isolation. This is the tool that surfaced the Stage 2 flakiness noted above — kept in the repo as a reusable regression check for the whole rotation (8-minute timeout, since clearing 5 stages sequentially takes a while), not a one-off.

Synthesizes every SFX and both music loops at runtime via **`Assets/Scripts/Audio/ProceduralSfx.cs`** (`AudioClip.Create` + sine/square/triangle waveform synthesis with attack/release envelopes) — there are no external audio assets yet. ### Nicknames, quit confirmation, clear times, and a controls hint

A further pass closing smaller "feels unfinished" gaps found by re-reading the whole flow end to end as a first-time player would:

- **`Assets/Scripts/Player/PlayerProfile.cs`** + **`PlayerNicknameNGO.cs`** — the connect screen (`GameFlowSceneSetup.BuildConnectUI()`) now has a nickname `InputField` (`NicknameFieldUI.cs`, prefilled from `PlayerPrefs` via `PlayerProfile.GetLocalNickname()`). `PlayerNicknameNGO` is an Owner-writable `NetworkVariable<FixedString32Bytes>` on `Player.prefab` — same pattern as `PlayerMovementNGO.horizontalInput` (no RPC needed, the owner just writes it directly on spawn). `PlayerLabelNGO` shows the nickname when set and falls back to the existing "P{rank}" otherwise, so bots and players who leave the field blank are unaffected. Not server-validated — display-only, and this project's threat model (friends on a small dedicated server) has no incentive to forge one. **`PlayerProfile` trims by UTF-8 *byte* count (`MaxBytes = 28`), not character count** — `FixedString32Bytes`'s real capacity is 29 UTF-8 bytes despite the name, and Korean is 3 bytes/char, so a naive character-count trim let a ~10-character Korean nickname overflow it and throw uncaught inside `OnNetworkSpawn` (which also skipped every later component's `OnNetworkSpawn` on that same object, since NGO's spawn loop has no try/catch around it). The connect screen's `InputField.characterLimit` derives from the same `PlayerProfile.MaxCharsWorstCase` constant rather than a separately hardcoded number.
- **`PauseMenuUI.OnQuitClicked()`** no longer shuts the `NetworkManager` down immediately — it opens a `QuitConfirmPanel` (Yes/No, same subpanel pattern as the Settings card) first. This is co-op session state shared with other connected players; an accidental ESC-then-click used to drop everyone instantly. Both subpanels are tracked through a single `Overlay` enum (not one bool per panel), so a future third dialog is one enum case + one `PanelFor()` mapping, not another parallel bool/Immediate-close/wrapper trio.
- **`StageClearUI`** times each attempt locally (`Time.time` at the clear banner's `OnEnable`/`ResetTimer()` vs. at the moment `stageCleared` flips) and compares it against a `PlayerPrefs`-backed personal best keyed by the same stage label `BuildStageUI` already assigns (`"Stage 1 · Gatekeeper"` etc.) — a per-client "NEW RECORD!" stat, not a synced/ranked leaderboard, so it needs no server plumbing. `StageManagerNGO.NotifyFailure()` (Stage 4's fail/retry path) calls `StageClearUI.ResetTimer()` so a failed attempt's elapsed time doesn't get folded into the next successful attempt's recorded time.
- **Lobby controls hint** — `CreateLobbyScene()` adds a small persistent "조작법 - ←/→ 이동, Space 점프" label. There was previously no in-game indication anywhere of the movement/jump keys.
- **`UITheme.WithAlpha(color, alpha)`** — the sanctioned way to make an opacity-tinted variant of an existing token (per the Style Guide's own "variety comes from mixing these tokens' weights/opacities, not from adding new colors"), instead of each call site inlining its own `new Color(token.r, token.g, token.b, alpha)`.

### Camera shake

`CoopCameraFollow.Shake(magnitude, duration)` adds a short, linearly-decaying random offset on top of the camera's normal followed position — the game's only moment-to-moment feedback beyond UI banners and SFX until now. The followed position is tracked separately (`currentFollowPosition`) from `transform.position` specifically so the shake offset never becomes the input to next frame's `SmoothDamp` (that would make the shake bleed into the follow smoothing and drift). Wired into `StageClearUI`'s existing `goalZone.stageCleared` callback — the same already-replicated moment the clear banner/SFX use, so every client shakes in sync with zero extra network traffic. Purely local/visual; call it from anywhere client-side for future feedback moments (`Camera.main?.GetComponent<CoopCameraFollow>()?.Shake(...)`, guarded for headless-server safety since a dedicated server has no camera).

### UI polish: button/panel juice

Every menu prior to this pass used flat `SetActive(true)`/instant color-tint button states — functional but reads as unfinished next to the rest of the "toy blocks on a white table" style guide. Two small reusable runtime components close that gap without touching any existing call site:

- **`Assets/Scripts/UI/UIButtonPunch.cs`** — a press-scale feedback component (`IPointerDownHandler`/`IPointerUpHandler`/`IPointerExitHandler`, scales to 0.92× on press and eases back via `Time.unscaledDeltaTime`). Added once at each button-factory call site (`GameFlowSceneSetup.CreateMenuButton()` — covers Resume/Settings/Quit/Back/quit-confirm/retry, since every one of those routes through that single helper — plus the connect screen's `ConnectButton` and small settings-gear button) rather than at every individual button, so any future button built through those factories gets the feedback automatically. Also implements `IPointerEnterHandler` to toggle an `Outline` tinted `UITheme.ColorHighlightRing` on hover — the style guide's dedicated hover/focus/selected token existed since the very first UI pass but had never actually been wired into any control until this. **`Assets/Scripts/UI/UIInputFieldFocusRing.cs`** applies the same ring to the nickname `InputField` via `ISelectHandler`/`IDeselectHandler` instead (Unity doesn't bubble pointer/select events to parent GameObjects, so this needs its own small component directly on the field rather than reusing `UIButtonPunch`).
- **`Assets/Scripts/UI/UIPunchIn.cs`** — a scale+fade pop-in (`RequireComponent(CanvasGroup)`, 0.85×/alpha-0 → 1×/alpha-1 over 0.16s ease-out-cubic) that triggers on `OnEnable`. Attached once to each card/banner GameObject at scene-build time (the stage-clear banner, the pause menu's `Card`/`SettingsPanel`/`QuitConfirmPanel`, the connection-lost card, the world map's `MapCard`/`StageIntroCard`) — existing `SetActive(true)` call sites in `StageClearUI`/`PauseMenuUI`/`WorldMapUI`/`ConnectionStatusUI` needed no changes at all, since `OnEnable` is the trigger.
- Both are additive/cosmetic only — no gameplay, netcode, or existing-script changes — so they carry effectively no risk to the already-verified stage-clear reliability; skip attaching either to any future world-space (non-UI) sprite, since `UIButtonPunch`'s `localScale` punch would fight `GameFlowSceneSetup.ApplySlicedSprite()`'s sliced-sprite sizing convention documented above.
- **`Assets/Scripts/Network/LoadingScreenUI.cs`** (the Lobby↔Stage scene-transition overlay) previously just snapped `SetActive` on/off. It now fades a `CanvasGroup` in/out over 0.2s instead (object stays active through the fade-out and only actually deactivates once alpha reaches 0, otherwise the fade would never be visible), and spins a rounded-ring `UI_LoadingSpinner.png` sprite continuously while shown — a static "로딩 중..." dot-cycle alone read as frozen on a slow transition.
- **`Assets/Scripts/UI/LobbyUI.cs`**'s countdown number now gets the same scale-pulse treatment as `ScoreboardUI`'s score updates, but only on an actual per-second countdown tick (`onlyCountdownTicked` — connected-count/state/selection changes swap the whole string instead and skip the pulse, since pulsing on every kind of text change would read as noise rather than a "tick").
- **Fullscreen/windowed toggle**: the Settings panel only ever had volume sliders — no display option at all, unlike almost every commercial PC game. `GameFlowSceneSetup.CreateToggle()` (same code-assembled-standard-Unity-UI-hierarchy pattern as `CreateSlider()`) adds a checkbox-style `Toggle` wired to `PauseMenuUI.OnFullscreenToggled()`, which sets `Screen.fullScreenMode` and persists the choice via `PlayerPrefs` (applied again on next launch in `PauseMenuUI.Awake()`, guarded `#if !UNITY_SERVER` since a headless dedicated server has no monitor — same guard `AudioManager` already uses for the same reason). Note: `Toggle` has no `SetValueWithoutNotify` (unlike `Slider`) — use `SetIsOnWithoutNotify` instead, a real compile error hit while adding this.

### Jump feel (coyote time + jump buffering)

`PlayerMovementNGO`'s jump used to require the server to see `isGrounded == true` on the *exact* physics tick `RequestJumpServerRpc` arrived — any earlier or later and the input was silently dropped, which reads as "unresponsive controls" and is especially punishing in a co-op puzzle game where a dropped jump can mean falling into a pit. `RequestJumpServerRpc` now just records a `jumpBufferedUntil` timestamp; `FixedUpdate` executes the jump once both a jump-buffer window (pressed recently, `JumpBufferTime = 0.12f`) and a coyote window (grounded recently, `CoyoteTime = 0.12f`) are satisfied — the ordinary "grounded, pressed now" case flows through the same check. All judgment stays server-side (still fully server-authoritative); this changes feel, not the trust model. `ExecuteJump()` resets `lastGroundedTime` to `-infinity` so a second jump press within the coyote window right after a jump can't chain into a double-jump.

### Performance pass (per-frame allocations and network chatter)

Found by an explicit audit of every `Update()`/`FixedUpdate()` in `Assets/Scripts`:
- **`PlayerSetupNGO.ActivePlayers`** (a static `List<GameObject>`, added/removed in `OnNetworkSpawn`/`OnNetworkDespawn`) replaces `GameObject.FindGameObjectsWithTag("Player")` calls that `CoopCameraFollow.LateUpdate()` and `BotController`'s `StageAuto`/`FollowNearest` modes were each making **every frame** (per bot, for `BotController` — multiplies with bot count), each allocating a fresh array to scan a scene that already knows its own player list via spawn/despawn events (already proven reliable by the verified late-join/disconnect edge cases).
- `BotController.GoalHalfWidth()` now reads a `goalCollider` cached alongside `goal` in the existing 0.5s `RefreshStageRefs()` gate, instead of calling `goal.GetComponent<BoxCollider2D>()` fresh on every call from the hot path.
- `GameFlowManager.Update()` only writes `lobbyCountdownRemaining.Value` (a `NetworkVariable`, replicated to every client on every write) when the *rounded* value actually changes, instead of every frame — the only consumer (`LobbyUI`) displays it rounded to the nearest second anyway.
- `CarryableKeyNGO.FixedUpdate()` caches the carrier's `Transform` once in `OnCarrierChanged` instead of doing a `NetworkManager.ConnectedClients` dictionary lookup every physics tick for as long as the key is carried; a destroyed/despawned carrier is detected via Unity's overridden null-check on the cached reference, not a re-lookup.

### Lobby ready button + auto bot-fill

The lobby used to auto-start a countdown the moment `ConnectedClientsIds.Count >= minPlayersToStart` (1 by default) — felt unfinished, and meant a solo player got dropped straight into 4-person content with no partners. Replaced with an explicit per-player ready button:

- **`LobbyUI.OnReadyClicked()`** toggles a client-local `localReady` bool and calls **`GameFlowManager.RequestReadyServerRpc(bool)`** (`RequireOwnership = false`, same reasoning as `RequestSelectStageServerRpc` — this `NetworkObject` is scene-placed and owned by no client). The server tracks who's readied in a `readyClientIds` `HashSet<ulong>`, mirrored into the replicated `readyCount` NetworkVariable purely for UI display (`LobbyUI` shows "N/M명 준비 완료").
- `GameFlowManager.Update()`'s old auto-countdown block is gone; a stage only starts once `readyClientIds.Count >= ConnectedClientsIds.Count` (i.e. **every** currently-connected client has readied — a client connecting mid-wait, having not readied yet, makes this condition false again on the very next frame, which is what cancels a pending fill-wait without any separate "new player joined" handling).
- If everyone's ready but total headcount is still under `requiredHeadcountToStart` (4 — the minimum every `BotController.StageAuto` solution assumes), the server starts a `fillWaitSeconds` (5s) wait (shown via the same `lobbyCountdownRemaining` NetworkVariable the old auto-start countdown used, now repurposed) before calling **`GameFlowManager.SpawnFillerBots(int)`** and starting the stage anyway.
- **Filler bots are not `-bot` processes** — `SpawnFillerBots` directly `Instantiate`s `NetworkConfig.PlayerPrefab` and calls `NetworkObject.Spawn()` (default ownership = `NetworkManager.ServerClientId`) entirely server-side, no transport connection involved. `BotController.MarkAsFillerBot()` (called before `Spawn()`, so it's already set when `OnNetworkSpawn()` runs) sets a private `isFillerBot` flag that `OnNetworkSpawn()` now checks alongside `BotProcess.IsBot` (`enabled = BotProcess.IsBot || isFillerBot`) — everything downstream (`StageAuto`, the movement/RPC path) is identical to a real `-bot` process, since on the server `NetworkManager.LocalClientId == NetworkManager.ServerClientId` for a plain `StartServer()` (confirmed directly in NGO's own `NetworkManager.StartServer()`), so `IsOwner` reads true for a server-owned object on the server instance and the usual `if (!IsOwner) { enabled = false; return; }` gate in both `PlayerSetupNGO`/`BotController` passes.
- **This broke rank-based role assignment for filler bots specifically, which is why `PlayerSetupNGO.GetRank(NetworkObject)` now exists**: every filler bot spawned this way shares the exact same `OwnerClientId` (the server's), so the old `OwnerClientId`-ascending rank calculation (`BotController.GetMyRank()`/`FindPlayerByRank()`) couldn't tell multiple filler bots apart — all rank 0 by that measure. Rank is now computed by `NetworkObjectId` order instead (unique per spawned object regardless of type), and `PlayerSetupNGO.MoveToSpawnPoint()`'s spawn-point index picks the same way (`NetworkObjectId % spawnPoints.Length`) so multiple filler bots don't all land on the exact same spawn point.
- **`PushableBlockNGO.requiredPushers` scaling and `GoalZoneNGO`'s "everyone reached the goal" check both moved from `ConnectedClientsIds.Count` to `PlayerSetupNGO.ActivePlayers.Count`** — filler bots aren't real transport connections, so the old headcount source silently excluded them, which would have left both gates permanently unsatisfiable by exactly the filler-bot count once any got spawned. `GameFlowManager.HandleLoadEventCompleted()` had the same bug for repositioning (iterated `ConnectedClientsIds`, so filler bots never got moved to a new scene's spawn points on transition) and now iterates `PlayerSetupNGO.ActivePlayers` directly instead.
- **Fill-amount is sized off total active players, not connected clients**, specifically so a lobby that already has leftover filler bots from a previous Lobby→Stage→Lobby cycle doesn't get topped up again into an ever-growing roster (`SpawnFillerBots(requiredHeadcountToStart - PlayerSetupNGO.ActivePlayers.Count)`, not `... - ConnectedClientsIds.Count`). Filler bots are never despawned once spawned — they persist for the rest of the session like a real `-bot` process would, which is an intentional simplification (nothing in the request asked for shedding them once real players arrive).
- **Now bot-verified against the real GCP server for the first time, and it immediately found two real bugs** — the very scenario this feature exists for (a small real-player group topped up by filler bots) had never actually run before this pass, and `FullRotationBotVerify`'s `StartHost()` methodology structurally can't exercise it (see the rank-0-phantom-host section above: with 4 real bot clients already meeting `requiredHeadcountToStart`, no filler bot ever spawns in that tool). Only a real 3-bot-client run against the deployed dedicated server actually exercises the fill path.
  - **Stage 2 (Block Carry) stall — found, root-caused, fixed, and re-verified live.** With 3 real bots + 1 filler bot (4 total, `requiredPushers=3`), the block reliably got stuck permanently at `overlap=2` a good distance short of its target (observed frozen at `x=22.96` for 4+ minutes straight, zero recovery). Root cause: `BotController.UpdateBlockPush()` set every pushing bot's `HorizontalInput` to a single blind global sign — `Mathf.Sign(target.x - block.x)` — applied identically to all bots regardless of their own position. This works fine as long as every bot stays behind the block, but a bot that gets physically shoved past the block's leading face (plausible with a Kinematic `MovePosition`-driven block pressed against several dynamic bodies at once) would then keep walking in that same fixed direction *away* from the block forever, with no way back — permanently short-staffing the required-pushers gate. Fixed by having each bot target its own standoff point behind the block (`block.x − pushDir·pushStandoffDistance`) rather than a bare direction, so a displaced bot's input sign flips and it walks back into formation instead of drifting off. Re-verified with the exact same 3-real+1-filler production scenario after the fix: Stage 2 now clears cleanly. `PushableBlockNGO`'s stuck-state log (`FixedUpdate()`) now also names which players are/aren't inside the push trigger and where every active player actually is, specifically to make this class of "who's missing" question answerable from the log alone next time.
  - **Stage 3 (Key Relay) — found a second, different, still-unfixed bug; deploy of the ready-button/fill feature is deferred until this is resolved.** In the same live production run, immediately after the Stage 2 fix, Stage 3 with the same 3-real+1-filler group never cleared: `KeyDoor1` cycled open/closed roughly once per network tick for 8+ minutes straight (273 opens, 273 closes, perfectly paired, zero progress) with no exceptions and no stage-clear. Not yet root-caused, but the leading hypothesis (unconfirmed) is physical crowding: `UpdateKeyRelay()`'s non-carrier waiters target almost the same spot the carrier holds (`doorX − 0.6`), so several bots converging there could be jostling the carrier back and forth across `KeyDoorNGO.openRange`'s ±1 unit boundary, which would explain rapid flicker without any logged error. **Production was rolled back both times this session** — first past the Stage 2 bug, then again past this Stage 3 bug — back to the pre-ready-button-feature build (`ServerBuild.backup2` → `ServerBuild`), which has no filler-bot code path and is the same build verified extensively before this feature existed. The ready-button/fill C# changes and scene regen are committed to this branch but **not currently deployed** — do not redeploy until Stage 3 is re-verified clean with a real filler-bot run.

**Gotcha hit building this while another session had the Editor open on the same project**: uncommitted edits to `BotController.cs` got silently clobbered multiple times mid-session by the other session's own saves (Unity doesn't merge concurrent writes to the same file — last write wins). The fix in the moment was to re-apply the edit and `git commit` it immediately afterward, minimizing the window; the durable fix is what `bot-verify-deploy`'s pre-flight step already checks (`tasklist | grep -i unity.exe` before touching the project) — if Unity is already running and you didn't start it, that's a live concurrent session, and running your own headless Unity pass (or trusting an uninterrupted multi-edit sequence on the same files) isn't safe until it closes.

### Physics / tag / layer config (`ProjectSettings/`)

These were hand-edited (not generated by the Editor) and are load-bearing:
- `Physics2DSettings.asset` — the `Player` layer's self-collision bit is explicitly re-enabled (it ships disabled in the Alteruna template this `ProjectSettings` baseline was copied from). Without it, players cannot stack/push each other, which breaks the core co-op mechanic.

## UI Style Guide

All in-game UI (menus, HUD, buttons, connect screen, any future dialogs) must follow this guide so the look stays consistent as features are added one at a time. Source: the actual `bundle.css` design tokens from the official PICO PARK 2 site (`https://picoparkgame.com/en/pp2/`), extracted directly from its CSS custom properties — not a guess from screenshots. Do not invent alternative colors/fonts/radii for new UI; extend this token set instead.

### Color tokens

| Token | Hex / value | Use |
|---|---|---|
| `color-primary` | `#48ad15` (grass green) | Primary brand color — main buttons, header/footer background, active states. This is specifically PICO PARK **2**'s series color (PP1 is orange `hsl(19 100% 65%)`, Super Pico Park is blue `#0280c1` — don't mix those in, this project follows PP2). |
| `color-ice` | `#4dd6fa` (sky blue) | Secondary accent — secondary buttons, links, highlights, icy/water-themed elements. |
| `color-bg` | `#ffffff` | Page/screen background. Keep UI backgrounds white, not dark — this is a bright, family-friendly palette, not a dark theme. |
| `color-bg-secondary` | `#e9fbdf` (pale mint) | Panel/card backgrounds, subtle section separation on top of white. |
| `color-fg` | `#132e05` (`hsl(100 80% 10%)`, near-black forest green) | Primary text color. Never pure `#000000` — always this warm dark green-black. |
| `color-white` | `#ffffff` | Text/icon color on top of `color-primary` fills. |
| `color-highlight-ring` | `#bfffde` (light mint) | `box-shadow: 0 0 0 2px` inset ring for focus/hover/selected states. |
| `color-shadow-25/50/75` | `rgba(0,0,0,.25)` / `.5` / `.75` | Layered darkening for the chunky "3D block" depth effect (see Shape below), not for flat drop shadows. |

Don't introduce new hues without a reason — variety comes from mixing these tokens' weights/opacities, not from adding new colors.

### Typography

- **Headings**: `Dosis`, weight **800** (extra bold), fallback `'M PLUS 1p', sans-serif`. Always **UPPERCASE**, `letter-spacing: 0.05em`, `line-height: 1.3`. Dosis is tall/condensed and geometric — this is what gives titles their toy-block punch.
- **Body / UI labels**: `M PLUS 1p`, weights 500/700/800. A soft, rounded sans that also covers Hangul reasonably — useful since this codebase's dev comments are in Korean and any dev-facing debug UI may need Korean text.
- **Icons**: `Material Symbols Rounded` (rounded fill style, not sharp/outlined) for any icon glyphs — matches the soft, friendly shape language.
- Both fonts are free on Google Fonts (`Dosis`, `M+PLUS+1p`); the actual `.ttf` files live in `Assets/Fonts/` and are imported as plain Unity `Font` assets used directly by legacy `UnityEngine.UI.Text` (see "UI Style Guide implementation" above) — not as TextMeshPro Font Assets, since TMP Essentials was never imported into this project.
- Both `NetworkSetupMenu.cs`'s (legacy scene) and `GameFlowSceneSetup.cs`'s (live `Bootstrap`/`Lobby`/`Stage01`) UIs apply these fonts/colors — see "Editor automation" above for how the latter reuses the former's helpers instead of duplicating them.

### Shape & depth

- **Corner radius**: `6px` is the default for buttons, cards, and pill-shaped nav items. `3px` for small/tight elements. `12px`–`20px` only for large feature panels, never for small controls.
- **Borders**: interactive pill/badge elements (e.g. nav buttons) use a **solid 3px border** in the foreground color, not just a fill — the "badge/sticker" look, not a flat Material-style button.
- **Depth**: avoid soft blurred drop-shadows. Depth comes from **layered flat `rgba(0,0,0,.25/.5/.75)` offsets** stacked to look like a chunky physical block/cube casting a hard-edged shadow — this matches the game's literal cube/box level geometry. A `0 0 0 2px inset` ring in `color-highlight-ring` is the only "glow"-style effect, reserved for hover/focus/selected.
- **No gradients for filling shapes** — flat color fills only. Gradients on the reference site are limited to thin decorative accents (a 2px white "shine" line, edge-fade masks) — not something to reach for by default.

### Layout & tone

- Generous whitespace, center-aligned content, clear vertical sections — not dense or cluttered.
- Bright, clean, minimal-but-playful, cooperative/family-friendly tone throughout. Every UI decision should read as "toy blocks on a white table," not "sci-fi HUD" or "dark fantasy."

### Art style (sprites/characters, for when placeholder art is replaced)

Simplified, round/blobby character shapes with thick clean outlines and flat saturated color fills; simple dot/shape facial features; no complex shading or gradients. Low visual complexity is a feature, not a limitation — it reads clearly at small sizes and is cheap for a solo dev to produce/reproduce consistently across many player-color variants (see `PlayerColorNGO`'s palette, exposed via the public `PlayerColorNGO.GetColor(int index)` so other UI — e.g. `ScoreboardUI`'s per-player swatches — stays in sync with actual in-game player colors instead of hardcoding its own copy of the palette).

## Deployment (GCP)

Dedicated server runs on Compute Engine, not Cloud Run — NGO's default `UnityTransport` uses raw UDP, which Cloud Run's HTTP(S)-only ingress cannot carry.

- Project: `filerpark` (billing enabled)
- VM: `filerpark-game-server`, `e2-small`, zone `asia-northeast3-a`, running 24/7
- Static IP: `34.50.24.161` (reserved as `filerpark-server-ip`)
- Firewall: `allow-ngo-udp` — ingress UDP `7777` from `0.0.0.0/0`, targets instances tagged `game-server`
- The client's `NetworkManager` → `UnityTransport` → Connection Data must point `Address` at `34.50.24.161`, `Port` `7777`.

**Gotchas hit deploying the real server (verified via `tcpdump` on the VM, not just "StartServer() returned true"):**
- `UnityTransport.ConnectionData.ServerListenAddress` defaults to `127.0.0.1` regardless of what `Address` is set to. `StartServer()` reports success either way, but nothing outside the VM can reach it unless the server explicitly sets `ServerListenAddress = "0.0.0.0"` before starting (see `NetworkBootstrapper.cs`'s `UNITY_SERVER` branch).
- A freshly built client `.exe` that's never been run has no Windows Firewall rule and gets its inbound UDP (the server's handshake replies) silently dropped, even though its own outbound packets reach the server fine — looks identical to a server-side problem from the client's logs alone. Needs explicit `New-NetFirewallRule` (in + out, UDP, `-Profile Any`) for the exact exe path.
- Deploying via `gcloud compute scp --recurse` from Windows uses PuTTY's `pscp` under the hood, which behaves differently from OpenSSH `scp`: destination must be an absolute remote path (`/home/<user>`, not `~`) — `~` is passed through literally and PuTTY doesn't expand it — and the destination directory is created from the local folder's own name, so scp `ServerBuild` to `/home/<user>` (not `/home/<user>/ServerBuild`, which double-nests).
- `nohup ... &` inside a single `gcloud compute ssh --command="..."` call routinely hangs the SSH session past the point the remote process has actually detached; don't treat that command's own timeout/hang as a failure signal — reconnect with a fresh `ssh --command` to check `ps aux`/logs independently.

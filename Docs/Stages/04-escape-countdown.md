# Stage 4 — 탈출 카운트다운 (Escape Countdown)

**테마**: 공동 생존 · **인원**: 4~6명 · **구현 상태**: 신규 컴포넌트 필요 — `RisingHazardNGO`, `StageManagerNGO` 확장(전원 도달 판정 + 낙오 실패 처리).

## 개요

바닥에서 용암(또는 좌측에서 다가오는 벽)이 서서히 차오른다. 전원이 발맞춰 골까지 가야 하며, 누군가 뒤처져 위험지대에 닿으면 스테이지 실패로 전원 재도전 — "제일 느린 사람에게 팀 전체 속도를 맞춰야 한다"는 압박감이 이 스테이지의 핵심 학습 목표다. 다른 3개 스테이지와 달리 **명시적인 실패 조건과 타임 프레셔가 있는 유일한 스테이지**.

## 신규 컴포넌트

### `RisingHazardNGO`
```csharp
public class RisingHazardNGO : NetworkBehaviour
{
    public float riseSpeed = 0.3f; // 초당 상승 속도(유닛)
    public float startDelay = 3f;  // 스테이지 시작 후 상승 시작까지 유예 시간

    // 서버 FixedUpdate: startDelay 경과 후 transform.position.y를 riseSpeed로 증가시키고
    // NetworkTransform으로 전파. 트리거 콜라이더가 Player와 닿으면 StageManagerNGO에
    // "탈락" 통보.
}
```

### `StageManagerNGO` 확장
- 기존에 "골존에 전원 도달"만 성공 판정하던 것을, 이 스테이지에서는 "낙오자 발생 시 즉시 실패 + 전원 스폰 지점으로 리셋 + `RisingHazardNGO` 위치 초기화"까지 처리하도록 실패 경로를 추가해야 한다. 다른 3개 스테이지는 실패 조건이 없으므로 이 확장은 스테이지별로 켜고 끌 수 있는 옵션(`hasFailCondition` 플래그)으로 설계한다 — `StageManagerNGO`를 스테이지마다 다시 짜지 않도록.

## 인원수 스케일링

- `riseSpeed`는 인원수와 무관하게 고정 — 대신 **맵 길이**를 인원수에 비례해 늘린다(인원이 많을수록 대열이 길어지고 흩어지기 쉬우므로, 같은 상승 속도라도 체감 난이도가 자연히 올라간다. 별도 파라미터 튜닝 없이 레벨 지오메트리만으로 스케일링).

## 레벨 레이아웃 (개념도, 좌→우 진행하며 아래에서 용암이 차오름)

```
[스폰]══════════ 골 방향 ════════════[골존]
  ▲ 용암(RisingHazardNGO)이 시간이 지날수록 이 라인 전체가 상승
  대열 전체가 이 라인보다 위에서 계속 전진해야 함
```

- 단순 직선 통로 + 중간중간 살짝 높은 턱(느린 사람이 더 처지게 만드는 자연스러운 장애물, 별도 기믹 불필요 — 지형만으로 "누가 느린지" 갈림).

## 진행 흐름

1. 전원 스폰. `startDelay`(3초) 동안 대형을 갖출 시간.
2. 용암 상승 시작. 전원 골 방향으로 이동.
3. 낙오자가 용암에 닿으면 즉시 실패 -> 전원 리셋.
4. 전원 골존 도달 시 성공.

## 승리/실패 조건

- 성공: 전원 골존 도달.
- 실패: 1명이라도 `RisingHazardNGO`에 접촉 -> 즉시 전원 실패, 리셋.

## 봇 자동 클리어 로직

공통 아키텍처: [bot-coordination.md](bot-coordination.md). 이 스테이지는 **역할 분담이 아니라 전원 동일 행동(GroupAdvance)이라 자동화하기 가장 단순**하다 — 역할 배정표가 사실상 1줄이다.

| 역할 번호 | BotMode | 대상 | 인원 |
|---|---|---|---|
| 0 ~ N-1 (전원 동일) | `GroupAdvance` | `Player` 태그 전체 (자기 진행도를 팀 최소 진행도에 맞춤) | 전원 |

- `GroupAdvance`의 페이스 제한 로직이 이 스테이지 자동검증의 핵심: 매 프레임 `GameObject.FindGameObjectsWithTag("Player")`로 전원의 x좌표를 읽고, `myProgress - teamMinProgress > allowedLead`면 전진을 멈추는 방식(속도를 늦추는 게 아니라 아예 멈췄다 가는 쪽이 "제일 느린 사람 기준"이라는 컨셉을 더 명확히 구현함).
- **자동 검증 신뢰도가 4개 중 가장 높음** — 이미 있는 `FollowNearest`의 "다른 플레이어 위치 읽기" 패턴을 그대로 재사용하고, 판정(낙오=실패)도 좌표 비교라 결정론적이다. `[StageValidation]` 로그로 "봇 N마리, 몇 초에 실패/성공했는지"를 반복 측정하면 `riseSpeed`나 맵 길이 튜닝을 봇 시뮬레이션만으로 반복 조정할 수 있다 — 이 프로젝트의 봇 시뮬레이션 취지에 가장 잘 맞는 스테이지.
- **사람 플레이테스트가 필요한 부분**: "정말 재밌는 압박감을 주는 `riseSpeed` 값"은 봇으로는 알 수 없다 — 봇은 항상 동일한 로직으로 반응하므로 체감 긴장감/재미는 결국 사람이 판단해야 한다. 봇 시뮬레이션은 "이 값에서 절대 못 깨는 건 아닌지(밸런스 하한선)"를 확인하는 용도로 쓰고, "얼마나 짜릿한지"는 사람 몫으로 남긴다.
